**Frequency**: Common

## Issue: AI-built web UIs default to Inter, lavender-indigo accents and dark mode with no light option. Give the tool a type and color choice up front, honor prefers-color-scheme, and check before ship.

> **One line:** You ask an AI tool for an app screen and get Inter (or the bare system sans), an indigo or lavender accent, and a near-black page hard-coded to dark, so a user whose phone is set to light mode still gets dark; the fix is to name the typeface and accent in the prompt, follow the user's color-scheme setting with a light, dark and system choice, and run a check that flags all three before merge.

## 1. In plain words
When you leave the font, accent color and theme blank, an AI tool fills them with the most common answers: Inter or the system sans, an indigo or lavender accent, and often a dark page. Each choice is fine alone. Together, and unchosen, they make the page look like every other AI build. The dark theme is often hard-coded, so the page ignores the user's own light or dark setting.

This page is about type, accent color and theme mode. The [default gradient look](./ui-default-gradient-look.md) covers purple gradients and frosted glass; neon-on-dark and aurora glows are a separate planned pattern.

## 2. What it looks like
**Without the fix** (builder prompting an AI tool, no review step)
```
Builder: Build the patient booking screen for Harbor Lane Dental in Tampa.
Tool:    Done. <html class="dark">, body bg-zinc-950, font Inter from Google Fonts.
         Buttons and links bg-indigo-500 / text-violet-300. No theme toggle.
Builder: Looks sleek. Ship it.
         (A 68-year-old patient's iPhone is set to Light. The page opens near-black
         anyway. The client's brand is navy and coral; neither appears. The office
         manager says it looks like the last three apps they were pitched.)
```
**With the fix** (type, accent and theme rules given up front, checker runs before merge)
```
Builder: Booking screen for Harbor Lane Dental. Font: Source Serif 4 headings,
         Source Sans 3 body. Tokens: --navy #1F3A5F, --coral #E4572E, --paper #FAFAF7.
         Follow the user's system theme; add a Light / Dark / System switch.
Tool:    :root { color-scheme: light dark }. Dark tokens under prefers-color-scheme.
         Switch stores the choice; with none stored, the system setting decides.
Checker: Fonts match brief. 0 off-token colors. Light and dark both render.
         Lowest text contrast in either theme is above 4.5:1. Pass.
```
The tool got a font, an accent and a theme rule instead of blanks, and the checker rendered both themes instead of trusting one screenshot.

## 3. Why it happens
- **The safest font is the most common one.** Anthropic calls this distributional convergence and names Inter, Roboto, Arial and system fonts as the overused set. Tailwind's own `font-sans` default is a system stack, so a page with no font choice ships the platform sans (section 4).
- **The indigo accent is inherited.** One developer's essay traces the purple and indigo accents to Tailwind UI's `bg-indigo-500` buttons that spread through tutorials (single, secondhand source; section 4).
- **"Dark" gets hard-coded instead of wired to the setting.** Tailwind's class-based dark mode applies dark styles whenever `class="dark"` sits on `<html>`. A generator that writes that class literally, with no `matchMedia` check and no toggle, locks every user into dark. Nothing in the build fails, and the builder's own laptop may already be in dark mode.

## 5. The fix
**The principle:** Never leave type, accent and theme mode to the tool's default; name them, follow the user's setting, and render both themes before ship.

**Do this**
1. **Name the typefaces before the first prompt.** One or two families with their roles, in the prompt or the project rules file (for example a Cursor rules file or `CLAUDE.md`). If the brand really uses Inter, say so and the check passes.
2. **The accent comes from a token.** Buttons, links and focus rings use a named brand token; no raw `indigo-*`, `violet-*` or `purple-*` utility or hex that is not mapped to a token.
3. **The page declares both schemes.** `:root` has `color-scheme: light dark`, or the page states in the PR note why it is single-scheme.
4. **With no stored choice, the system setting decides.** Dark styles apply through `prefers-color-scheme` or through a class set from `matchMedia('(prefers-color-scheme: dark)')`. A literal `class="dark"` on `<html>` with no script and no toggle fails.
5. **Offer Light, Dark and System, and remember it.** A visible switch stores the user's choice; "System" clears it.
6. **Both themes pass contrast.** Every text pair measures at least 4.5:1 (3:1 for large text) in light and in dark.
7. **Run the check on every generated screen before merge, and watch for the second default.** Log each flag with screen, rule and outcome. If the tool swaps Inter for Space Grotesk or indigo for another stock accent with no brief behind it, flag that too.

**Reference design: project rules block** (paste into the tool's project instructions)
```
Fonts: use only the families in styles/tokens.css (--font-display, --font-body). Do not add other font imports.
Colors: use only color tokens. No indigo, violet or purple utilities unless a token maps to them.
Theme: set :root { color-scheme: light dark }. Follow prefers-color-scheme when no choice is stored.
Never hard-code class="dark" on <html>. Add a Light / Dark / System switch that stores the choice.
If no font or palette is given, ask for one before generating, and say which defaults you are avoiding.
```

**Reference design: review checklist** (each row is pass/fail)
| Check | How | Fails if |
|---|---|---|
| Font choice | Read computed `font-family` of `body` and first `h1`; compare to the brief | Inter, Roboto, Arial or bare system stack with no brief or PR reason |
| Accent token | Scan CSS and class names for color utilities and hex | Any accent not in tokens |
| Scheme declared | Look for `color-scheme` on `:root` or a meta tag | Missing, with no single-scheme reason |
| Follows system | Load with emulated `prefers-color-scheme: light`, then `dark`, no stored choice | Page looks the same in both |
| Switch | Find a control with Light, Dark and System; reload after choosing | Missing, or choice lost on reload |
| Contrast in both | Render each theme; measure every text pair | Below 4.5:1 (3:1 large) in either |

**Moves** (see [conversation moves](../../../solutions-library/conversation-moves.md)). Here the "conversation" is the builder prompting the AI tool, or the checker reporting to the builder. The moves are adapted, and the fit is our judgment.
| Move | When, in this pattern |
|---|---|
| Ask one clarifying question | The builder asks for UI with no font or palette: the tool asks for them before generating. |
| Offer choices: 2-4 options plus "Something else", free text open | The checker flags a default font or forced dark: "Use brand tokens", "Keep it: record the reason", "Ask a designer", "Something else". |
| Admit uncertainty and show how to check | The checker cannot emulate the color-scheme setting (a static screenshot only): it says so and names the manual check. |
| Hand off to a person | The flag is about brand direction, not a rule break (see hand-off rule). |

**Don't over-correct.** Inter, system fonts, indigo and dark themes are not banned. A system stack needs no font download, and a brand may use Inter or indigo on purpose. A dark-first product, such as a video player, can default to dark if it still honors the setting or records why. Do not strip a chosen font to pass a lint, and do not trade one stock font for another. The rule is "chosen and the user's setting honored", not "never Inter".

**Hand-off rule.** When the brief has no font or palette and no brand guide exists, or a flagged default is kept twice with "brand" as the reason, a human designer picks the type and accent and records them as tokens. The checker does not pick fonts or brand colors.

## 7. Metrics: how to spot it in production
Targets are starting points to tune on your own data, unless a source is given.
| Metric | Target | How to measure | Alert at |
|---|---|---|---|
| **Flagged generated screens shipped with no recorded reason** (primary, proposed) | Under 10% | Checker log per PR: screens flagged for font, accent or scheme merged with no reason note, divided by generated screens reviewed | Over 20% |
| Screens that ignore the system setting | 0 on main | Headless render with emulated light and dark, nothing stored; compare background color | Any |
| Screens with no Light / Dark / System switch | 0, or recorded single-scheme reason | DOM scan for the switch; reload test for persistence | Any |
| Text below WCAG contrast in either theme | 0 | Render each theme; measure every text pair | Any |
| Off-token accent colors | 0 on main | Static scan of CSS and class names against tokens | Any |
| Chosen fonts removed in error (counter-metric) | 0 | Designer reverts of checker-driven font or theme changes | Any |

### Detection signals (proposed, not yet calibrated)
Signals in generated code and the checker log. Treat them as proposed until checked against human-labeled screens.
| Signal | Where it shows | Counter-signal (what it could be instead) |
|---|---|---|
| Computed `font-family` of `body` and first `h1` both start with Inter, Roboto, Arial or a system stack, and the brief names no font | Rendered page | The brand guide specifies that font |
| `class="dark"` written on `<html>` in source, with no `matchMedia` call and no stored-theme read | Generated layout file | A dark-only product with the reason in the PR note |
| No `color-scheme` property and no `prefers-color-scheme` query anywhere in CSS | Generated CSS | A light-only internal tool where the team chose one scheme |
| Accent built from `indigo-*` or `violet-*` utilities, or matching hex, with no token | Generated CSS or class list | A token file that maps the brand accent to indigo |
| Same font and accent pair across unrelated projects from the same tool | Hash of font and accent values per project | A team that shares one design system on purpose |

**Starter rule:** every generated screen uses the brief's fonts and token accent, declares `color-scheme: light dark`, and follows the user's system setting until the user picks Light or Dark.

## 9. Common questions
### Why do all AI generated websites use the Inter font?
With no font named, the model picks the most common one in its training data. Anthropic names Inter, Roboto, Arial and system fonts as its model's defaults (section 4). Name your typefaces in the project rules (rule 1).

### Is using Inter bad?
No. Inter is a tell only when nobody chose it and it matches every other AI build. If your brand uses it, record that and move on.

### How do I stop v0, Lovable or Cursor from making my site dark mode only?
Put the rules block from section 5 in the project instructions, and check for a hard-coded `class="dark"` on `<html>`. With no stored choice, dark should follow `prefers-color-scheme` (rule 4).

### How do I make my site follow the system dark mode setting?
Set `color-scheme: light dark` on `:root`, put dark colors under `@media (prefers-color-scheme: dark)`, or set a `dark` class from `matchMedia` when no choice is stored. Tailwind and shadcn/ui both document this (section 4).

### Should my site default to dark mode or light mode?
Follow the user's setting. NN/g reports that light mode tends to read better for people with normal vision, while some users with cataracts read faster in dark, and recommends letting users switch (section 4).
