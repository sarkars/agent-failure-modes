## 1. What already exists
| Area | What the source says | Read | Type | What it means for us |
|---|---|---|---|---|
| Failure taxonomies | [MAST](https://arxiv.org/abs/2503.13657) (Berkeley et al.): 14 failure modes in 3 clusters (system design, inter-agent misalignment, task verification), built from 150 traces with annotator agreement kappa = 0.88; a dataset of 1,600+ annotated traces from 7 multi-agent frameworks; an LLM-as-judge annotator | Abstract | Research preprint | Real annotated traces are something this library lacks. The first pass said "200+ tasks" and "1,642 traces"; the abstract says 1,600+ traces, and I did not confirm the other figures |
| Failure taxonomies | [TRAIL](https://www.patronus.ai/blog/introducing-trail-a-benchmark-for-agentic-evaluation) (Patronus AI): a taxonomy of over 20 agentic error types, and 148 human-annotated traces with 841 errors, built on GAIA and SWE-Bench; the vendor reports best joint accuracy of 11% (Gemini 2.5 Pro) | Whole page | Vendor | Built on general and coding tasks, not customer conversations. The taxonomy itself is in the paper, which I did not open |
| Failure taxonomies | [AdaMAST](https://arxiv.org/abs/2607.16387) (2026 preprint): an agent system should keep an explicit failure taxonomy induced from its own traces, with no hand-authored codes; it reports gains on SWE-bench Verified Mini (60% to 70% with taxonomy feedback over free-text reflection) and other benchmarks | Abstract | Preprint, not peer-reviewed | It argues for trace-induced codes. The first pass said it argues that fixed catalogs like MAST are limited; the abstract does not say that, so I dropped the claim |
| Failure lists | [vectara/awesome-agent-failures](https://github.com/vectara/awesome-agent-failures) | **Not opened** (repository access was refused in this session) | Community | The first pass called it the closest in spirit and gave a star count from a third-party tracker. Neither is verified; a person should check it |
| Incident catalogs | [AI Incident Database paper](https://arxiv.org/abs/2011.08512) (McGregor, 2020): a collection of real-world AI failures with faceted and full-text search, over 1,000 incident reports at the time | Abstract | Research | Incident collection is not new. The paper is from 2020, so the current count is not known from this source |
| Incident catalogs | [ARE Incident Database write-up](https://dev.to/vdalal/i-catalogued-32-real-ai-agent-failures-then-marked-the-ones-we-cannot-stop-40k8) (a security vendor's author): 32 agent failures with sources, each mapped to an OWASP Agentic Security Initiative category, with the vendor's own coverage flag per entry | Whole page | Vendor blog, single author | Sourced, categorized incidents already exist for security failures. I did not open the database itself |
| Build guides | [Anthropic, *Building effective agents*](https://www.anthropic.com/engineering/building-effective-agents) separates workflows (predefined code paths) from agents (LLMs directing their own process), and lists customer support among its example applications. [OpenAI's practical guide](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) defines agents and covers when to build one, design foundations, and guardrails | Whole pages (text extracted) | Vendors | Generic "how to build" is covered by the biggest names. Google's Agents Companion, listed in the first pass, was **not opened** |
| Customer-service benchmarks | [τ-bench](https://arxiv.org/abs/2406.12045): simulated user conversations with a tool-using agent and domain policies, scoring end database state, with a `pass^k` reliability metric; it reports that gpt-4o-class agents succeed on under 50% of tasks and under 25% on pass^8 in retail | Abstract | Research | Measures task success and consistency, not tone, handoff, or accessibility. The abstract names retail; it does not name an airline domain. tau2-bench and Hyper-τ-bench were **not opened**, so I drop the Hyper-τ-bench figures (23.9% and 82.2%) |
| Customer-service handoff | A TechRxiv preprint, QiscusCS: a manually annotated set of 4,000+ utterances from 100 customer-service dialogues for handover evaluation. An Alibaba field-experiment paper (arXiv 2605.14830) rates post-escalation empathy on a three-point scale | **Summary only** (TechRxiv page returned 403; Alibaba paper not opened) | Preprints | Found in the second search. If accurate, "no handoff benchmark" is wrong: a handover dataset exists, though neither source seems to score handoff quality or tone together |
| Self-improvement research | [Survey of self-evolving agents (2025)](https://arxiv.org/abs/2507.21046): organizes the field by what, when, and how to evolve; covers evaluation and flags safety and scalability as open challenges. The Darwin Gödel Machine ([paper](https://arxiv.org/abs/2505.22954)) improves SWE-bench from 20.0% to 50.0% and Polyglot from 14.2% to 30.7%, with sandboxing and human oversight | Abstracts | Research | Heavily covered. The first pass said the DGM authors warn of misalignment from benchmark-optimized self-modification; the abstract only mentions safety precautions, so that claim is unverified |
| Self-improvement in practice | [OpenAI self-evolving agents cookbook](https://cookbook.openai.com/examples/partners/self_evolving_agents/autonomous_agent_retraining): a repeatable retraining loop, grounded in a regulated healthcare documentation task, with an optional GEPA prompt-optimization step | Intro and structure | Vendor | The basic loop is published. Braintrust, Arize, and Latitude posts (first pass) were **not opened** |
| Self-improvement with gates | [GRASP](https://arxiv.org/abs/2605.29668): improvement as edits to a bounded skill library, each admitted only if it nets an improvement on a held-out probe under a hard regression budget; tested on two FHIR clinical benchmarks, with MedAgentBench for gpt-oss-120b rising from 40.6% to 88.8% | Abstract | Preprint | Found in the second search. It is the closest thing I found to a gated, failure-driven loop. It targets procedural reliability in clinical tools, not customer conversation behavior |
| Self-improvement governance | [TrueFoundry playbook](https://www.truefoundry.com/blog/self-evolving-agents-enterprise-governance-playbook): self-changes land as separate candidate versions, pass an evaluation gate and, above a threshold, human approval, with versioned artifacts and rollback; the loop itself needs a budget and a watchdog. [Runtime governance paper](https://arxiv.org/abs/2603.16586): treats the execution path as the unit of governance and compliance policies as functions of identity, partial path, and proposed action | Whole page; abstract | Vendor; preprint | The "propose, evaluate, gate" design is published. The first pass said the governance paper argues that in-agent guardrails cannot be audited independently; the abstract does not say that, so I reworded it |

## 3. Will this content stand out? A second verdict
| Content | Verdict | Why |
|---|---|---|
| A large failure catalog | **Will not stand out on its own** | MAST, TRAIL, incident databases, and (unverified) community lists exist. MAST has annotated real traces we lack |
| A generic "how to build an agent" guide | **Will not stand out** | Anthropic and OpenAI have published guides (both opened) |
| A generic self-improving-agent write-up | **Will not stand out** | A survey, a cookbook, GRASP, and a governance playbook exist |
| Failure-first human-side coverage: handoff, refusals, tone, accessibility, wrong channel, with tests | **Plausible gap, narrower than first thought** | Two searches found task-success benchmarks (τ-bench), a handover dataset (summary only), and an empathy rubric (summary only), but no benchmark covering tone, refusals, or accessibility together. Unverified beyond two searches |
| A self-correcting customer-facing agent whose learning signal is a failure library, with a stated policy on what it may change | **Plausible gap, high effort** | GRASP groups failures and gates edits, the playbook covers gates and approval, and the loop is published. I found no implementation tied to a named customer-conversation failure library. Needs a real build and real results |
| Real traces and anonymized transcripts | **Strongest differentiator, not yet available** | It is what MAST's value rests on |

## 4. Is a guide (workstream 11) still worth writing?
**Recommendation, for a person to confirm:** do not write a generic guide on building or self-improving agents; the sources above already cover it. If a guide is written, keep it narrow: how to use a failure library as the gate for changes to a customer-facing chat agent, citing GRASP and the governance playbook, with the HMI patterns and tests as the library. Lower priority than the pattern queue.
