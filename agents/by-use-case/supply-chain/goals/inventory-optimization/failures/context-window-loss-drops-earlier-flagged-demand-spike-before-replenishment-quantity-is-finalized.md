# Context-Window Loss Drops Earlier-Flagged Demand Spike Before Replenishment Quantity Is Finalized

## Issue: In a Long Inventory-Planning Conversation Spanning Many SKUs, an Anomalous Demand Spike for a Specific SKU That the Agent Itself Flagged Early in the Session Fails to Carry Through to That Same SKU's Replenishment-Quantity Calculation Performed Many Turns Later, With the Agent Computing the Quantity as If the Spike Had Never Been Identified

**Frequency**: Occasional

**Symptoms**
- A SKU's final replenishment quantity, computed late in a long planning session, matches what a standard demand baseline would produce, with no adjustment for an anomalous demand spike the agent explicitly flagged for that same SKU earlier in the same session
- Asking the agent, immediately after the replenishment calculation, whether it accounted for the earlier-flagged spike surfaces an acknowledgment that it did not carry the flag forward into the calculation
- The drop is more likely the further back in the conversation the spike was flagged relative to the turn that triggers the replenishment calculation, and is not observed when the same SKU's calculation is requested in a short, isolated conversation immediately after the spike is flagged
- Re-flagging the same spike immediately before the replenishment-quantity turn, in an otherwise identical session, produces a quantity that correctly incorporates it
- Inventory planners who do not cross-check the final replenishment quantity against the session's own earlier flags proceed to order a baseline quantity that does not cover the flagged spike, and the SKU experiences a stockout shortly after replenishment despite the spike having been correctly identified earlier in the same session

**Root Cause**
As a planning conversation accumulates turns across many SKUs, the model's effective use of information earlier in the context window degrades for content that is not the most recent or most repeated, including a flag the model itself generated; the replenishment-quantity computation, when triggered many turns later, draws on demand-baseline inputs without independently re-confirming whether an open anomaly flag exists for that specific SKU. Because flags are represented only as freeform statements within the conversation history rather than as a structured, persistent record tied to the SKU, an unreinforced flag is effectively no longer available to the computation that needs it.

**Example**
```
Turn 8: Inventory-optimization agent flags an anomalous demand spike for SKU-4471, noting it should be factored into the next replenishment calculation
Turn 9-40: Planner and agent continue an extended session covering replenishment calculations for dozens of unrelated SKUs
Turn 41: Planner requests the replenishment-quantity calculation for SKU-4471
Agent computes the quantity from the standard demand baseline, with no reference to the spike it flagged at turn 8
Planner accepts the quantity without cross-checking it against the agent's own earlier flag
SKU-4471 stocks out within the replenishment cycle, despite the spike having been correctly identified 33 turns earlier in the same session
```

**Key Statistics**
| Finding | Source |
|---------|--------|
| Empirical evaluation of language models on long-context tasks finds that performance on information located earlier in a long context degrades measurably relative to more recent information, regardless of whether that information was originally generated by the model itself or supplied by a user | [Lost in the Middle: How Language Models Use Long Contexts](https://arxiv.org/abs/2307.03172) |
| Multi-turn conversation evaluation finds that LLMs systematically lose track of facts and flags established earlier in an extended conversation, with reliability degrading as conversation length and turn count increase | [LLMs Get Lost In Multi-Turn Conversation](https://arxiv.org/abs/2505.06120) |
| Persistent memory mechanisms for autonomous LLM agents are identified as a distinct architectural requirement precisely because relying on in-context-only flags causes earlier-identified anomalies to go unincorporated in long-running, multi-item planning sessions | [Memory for Autonomous LLM Agents: Mechanisms, Evaluation, and Emerging Frontiers](https://arxiv.org/html/2603.07670v1) |

**Contributing Factors**
- Anomaly flags raised by the agent are represented only as freeform conversation turns, with no structured, persistent record tied to the specific SKU that a later computation would automatically check
- Replenishment-quantity computation does not require an explicit check for open anomaly flags on the target SKU before proceeding from the standard demand baseline
- Planners default to trusting the final replenishment quantity without independently cross-checking it against the session's own earlier flags for that SKU

---

## Mitigation Strategies

1. **Structured Per-SKU Anomaly-Flag Ledger**: Maintain anomaly flags as a structured, per-SKU record outside the raw conversation transcript, persisting until explicitly resolved or cleared, rather than as freeform statements within a long session
2. **Mandatory Open-Flag Check Before Replenishment Calculation**: Require the agent to check the structured ledger for any open anomaly flag on the target SKU before finalizing a replenishment-quantity computation, and to explicitly incorporate or justify overriding it
3. **Flag-to-Calculation Linkage Requirement**: When an anomaly flag is raised, require it to remain visibly linked to the SKU's next replenishment calculation until explicitly addressed, rather than relying on conversational recall
4. **Replenishment-Output Cross-Check Against Open Flags**: Before a replenishment quantity is finalized, automatically diff the SKU against the structured flag ledger and surface any unaddressed open flag for planner review

### Metrics
- Rate of replenishment-quantity computations for SKUs with an open anomaly flag that show no adjustment from the standard demand baseline
- Mean conversation distance (turns) between an anomaly flag and the replenishment-quantity computation, for cases later found to have dropped the flag
- Stockout rate for SKUs with a previously flagged, subsequently dropped demand anomaly

### Alerts
- A replenishment-quantity computation for a SKU with an open, unresolved anomaly flag shows no incorporation of that flag → P1
- A structured-ledger cross-check flags an unaddressed open anomaly at replenishment finalization and is overridden without justification → P2
- Flag-loss rate across all multi-SKU planning sessions exceeds the defined threshold for a rolling window → P3
